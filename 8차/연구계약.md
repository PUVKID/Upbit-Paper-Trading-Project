# 8차 반복 학습 계약

## 입력과 계보

1. 7차 `read_parent()`로 완료 manifest, 전체 checkpoint 파일 해시, CUDA·가중치 변화 증거와 부모 계보를 엄격히 검사합니다. 부모가 없거나 손상되면 거부하며 공개 사전학습 원본으로 fallback하지 않습니다. 기존 legacy 완료 형식도 7차 reader 정책 그대로 지원합니다.
2. 초기 50GB 완료 근거는 기존 `initial_completion()`으로 검사합니다. 이후 2GB 증분 수집 대기는 이 초기 완료와 별개입니다. 외부 원본 전체를 추가학습했다고 주장하지 않습니다.
3. 부모 manifest의 train/tune 기간을 그대로 고정합니다. Upbit 5개 시장의 실제 5분봉을 Linux SQLite 읽기 전용으로 각 기간 따로 추출합니다. validation 기간을 조회해 입력으로 사용하지 않습니다.
4. 보호·소비 기간, 성공/실패 7차 평가 예약, 부모 계보의 validation과 보호 기간을 제외합니다. 봉 자체가 금지 기간에 겹쳐도 제외하며 결측을 보간하거나 공백을 넘는 창을 만들지 않습니다. 모든 시장의 train/tune에 context+horizon 이상인 연속 구간이 필요합니다.
5. 7차 부모가 과거에 평가 자료에 노출된 이력은 사라지지 않습니다. 이번 학습·튜닝·재로드 probe에 그 구간을 다시 넣지 않으며, 이를 미노출 모델이나 새 독립평가라고 표현하지 않습니다.

## 10회 실행

- 반복 수 10, fit당 50 step, batch 8, context 192, horizon 12, learning rate 1e-6은 설정 검사로 고정됩니다. 각 fit은 새로운 optimizer를 사용하며 직전 완료 가중치만 이어갑니다. optimizer 중간 resume는 지원하거나 주장하지 않습니다.
- 매회 디스크 여유와 STOP·시간을 확인하고 직전 checkpoint를 실제 로드합니다. 첫 회차는 7차 실행의 after-weight 해시, 이후는 직전 회차의 after-weight 해시와 비교합니다.
- 공식 fit이 복제한 실제 Trainer 모델의 첫 step 전 CUDA 검사는 7차 ChronosRuntime callback을 재사용합니다. CPU fallback은 없습니다.
- 매회 50 step 완료·유한 손실·가중치 변화, checkpoint 파일 해시, 재로드 가중치 해시, 저장 전후 **train context만** 사용한 예측 일치를 검사합니다. 예측은 저장 검증이지 성능평가가 아닙니다.
- 두 runner lock은 7차 다음 8차 순서로 획득합니다. 두 STOP 파일과 SIGINT/SIGTERM을 보존하며 협력적 guard로 최대 5시간을 제한합니다. 단일 GPU/파일 I/O 호출을 즉시 강제 종료하는 보장은 없습니다. 디스크 여유는 최소 20GB이며 자동 정리·삭제는 없습니다.
- 회차 완료 manifest를 원자 저장한 뒤 완료 수를 올립니다. 완료 전 실패는 해당 fit을 완료 수에 넣지 않습니다. 전체 종료·표시 파일 I/O가 실패하면 비정상 종료하고 원문을 보존하며 자동 재훈련하지 않습니다. 임의 지속 I/O 장애에서 표시 저장까지 보장하지 않습니다.
- attempt.json은 모델 로드 전의 `fit_preparation` 준비 기록이며 state는 prepared입니다. fit 호출이나 완료 횟수를 미리 기록하지 않습니다. 실제 완료 횟수는 50 step·가중치 변화·저장 재로드 검사를 마친 완료 manifest로만 집계합니다. 로드 실패는 완료 0회입니다.
- 회차 commit 뒤 상태 캐시 저장이 단발 또는 지속 실패하면 원문을 먼저 보존하고, aggregate에는 오류 상태와 확인된 완료 수를 별도 원자 저장합니다. CLI는 실패이며 재실행을 거부합니다. 캐시 파일 자체를 계속 쓸 수 없으면 그 파일은 오래된 값으로 남을 수 있습니다. API의 캐시 보정은 부모 담당이며 이 실행기가 UI 정상 표시를 보장하지는 않습니다. aggregate까지 지속 I/O 실패라면 원문·회차 manifest로 직접 진단해야 합니다.

## 상태 및 결과

`8차/work/status.json`은 flat dict입니다. 대시보드의 별도 `training_repetition` API 연결은 부모 담당입니다.

| 필드 | 의미 |
|---|---|
| rep_index / total_repetitions | 현재 회차 1~10 / 고정 10 |
| completed_repetitions | 검증된 완료 manifest 수 0~10 |
| step / total_steps | callback의 누적 step 0~500 / 고정 500 |
| state / stage | running·training·complete·waiting·stopped·error / extract·finetune·verify·complete |
| loss | 현재 fit의 유한 손실; fit 시작 전 null |
| model_id / run / device | 모델·batch 식별자 / 실제 CUDA 장치 |
| rows / context_length / batch_size / learning_rate | 고정 입력 행 수 / 192 / 8 / 1e-6 |
| checkpoint_verified | 현재 회차의 저장·재로드 검사 완료 여부; 성능 검증 뜻이 아님 |
| evaluation_performed / candidate_ready / promote | 항상 false |
| metrics 및 개별 MAE·direction·net_return·trades | 항상 null |

완료 checkpoint는 `unvalidated_train_only`이며 평가 또는 승격 후보로 취급하지 않습니다. 7차 상태·knowledge·코드, 기존 current와 모의 장부는 변경하지 않습니다. 7차 runner.lock만 상호 배제를 위해 열고 닫습니다. UI·backend·publication은 이 구현 범위 밖입니다.

## 확인 근거

수리71은 8차에서만 공식 `extract_model_from_parallel(..., keep_fp32_wrapper=False)`로 학습 반환 모델과 재로드 모델의 forward를 FP32 추론 모드로 정규화합니다. 전후 파라미터 해시 불변과 CUDA·eval·래퍼 제거·같은 추론 모드를 확인하며 rtol/atol은 각각 1e-5 그대로입니다. 저장 전 probe·가중치·파일 해시는 모델 해제 전에, 재로드 probe는 별도 파일에 먼저 저장합니다. 파라미터/모드/context/파일/예측 비교 결과를 원자 기록한 뒤 각각 다른 오류로 보고합니다.

명시적 첫 회차 복구는 수리70 소스 해시, 원래 요청·입력·부모·실패, 기존 무학습 진단의 9개 파일 해시, checkpoint-50의 global_step=50과 가중치 일치를 검사합니다. 새 무학습 probe와 manifest는 기존 진단 원문의 SHA256에 결합됩니다. 첫 회차 추가 fit은 0이며 원래 학습 1회가 소비된 상태에서 rep2~10만 최대 9회 실행합니다. 원래 실패는 보존하고 `original_before_after_probe_verified=false` 및 `recovered_after_reload_check`를 명시합니다. 이후 복구 자체의 실패도 자동 재훈련하지 않습니다. 기존 원본 미완료 completion은 덮지 않고 별도 recovery-first aggregate에 복구 1회+후속 완료 수를 기록합니다. 7차 및 운영 포인터는 변경하지 않습니다.

공식 [Chronos2 pipeline 소스](https://github.com/amazon-science/chronos-forecasting/blob/main/src/chronos/chronos2/pipeline.py)의 fit·로컬 checkpoint 계약과 프로젝트 7차에서 이미 실측한 고정 패키지 조합을 재사용합니다. 최신 main 소스를 고정 설치판의 실행 증거로 대신하지 않습니다. 실제 8차 GPU 학습 성패와 10회 완료 수는 부모의 승인 실행 이후 산출물로 확인해야 합니다.
